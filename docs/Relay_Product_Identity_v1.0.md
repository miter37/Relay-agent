# Relay Product Identity

## 사람과 AI Agent가 함께 일하기 위한 업무 설계·실행·검증 시스템

- **Document status:** Product identity and philosophy
- **Version:** 1.0
- **Date:** 2026-08-04
- **Product:** Relay-agent
- **Related basis:** `Relay_GUI_Development_Plan_v1.3`

---

## 0. 이 문서의 목적

이 문서는 Relay가 무엇인지, 왜 존재하는지, 어떤 방향으로 발전해야 하는지를 정의한다.

기존 GUI 개발계획은 RelayEngine, 로컬 daemon, SQLite 실행 이력, CLI·GUI·Schedule의 공유 기록, 결과·로그·파일·이벤트 관리 등 제품의 실행 기반을 구체화했다.

그러나 Relay가 장기적으로 어떤 제품이 되어야 하는지 설명하려면 기능 목록만으로는 충분하지 않다.

Relay는 단순한 멀티 Agent 실행기, 코딩 Agent의 GUI, 일정 실행 도구 또는 AI 채팅 애플리케이션이 아니다.

Relay는 다음 질문에 답하기 위해 존재한다.

> 사람이 AI Agent에게 실제 업무를 위임하려면, 그 업무는 어떤 구조로 설계되고 실행되며 검증되어야 하는가?

이 문서는 그 질문에 대한 Relay의 답이다.

---

# 1. 한 문장으로 정의하는 Relay

> **Relay는 사람과 AI Agent가 업무를 Task로 나누고 Project로 설계하며, 각 단계의 결과물·검증·승인·피드백을 기록하는 Work Agent 시스템이다.**

더 짧게 표현하면 다음과 같다.

> **Design the work. Inspect the checkpoints.**

Relay는 Agent의 모든 생각을 사람이 따라가도록 만들지 않는다.

대신 사람이 업무의 목적과 구조를 설계하고, Agent가 각 Task 안에서 자율적으로 일하며, 중요한 결과물 경계에서 사람과 다른 Agent가 검증·승인·보완하도록 만든다.

# 2. Relay가 해결하려는 문제

## 2.1 현재 AI 제품은 대부분 Session을 중심으로 만들어졌다

현재의 Chat AI와 Coding Agent는 대체로 Session 또는 Thread를 기본 단위로 사용한다.

Session에는 다음이 함께 섞여 있다.

- 사용자의 요청
- 추가 질문
- Agent의 설명
- 중간 시도
- 오류
- 수정 요청
- 도구 실행 결과
- 최종 답변
- 생성된 파일
- 다음 대화를 위한 맥락

이 구조는 탐색적 대화나 코딩 작업에는 유용하다.

하지만 반복되는 실제 업무를 관리하는 기반으로는 한계가 있다.

사용자는 시간이 지난 뒤 다음을 알고 싶어 한다.

- 어떤 업무를 실행했는가
- 언제 실행했는가
- 누가 또는 어떤 Agent가 수행했는가
- 어떤 입력 자료를 사용했는가
- 무엇이 결과물로 만들어졌는가
- 어느 단계가 실패했는가
- 누가 결과를 검증하거나 승인했는가
- 이 결과물이 이후 어떤 업무에 사용됐는가
- 같은 업무의 결과가 시간에 따라 어떻게 변했는가

Session은 이러한 질문에 답하기 위한 데이터 구조가 아니다.

Session의 목적은 대화를 이어가는 것이다.

Relay의 목적은 **업무를 남기는 것**이다.

## 2.2 AI가 많은 것을 출력한다고 해서 사람이 많은 것을 이해하는 것은 아니다

Agent는 이미 긴 추론 기록, 작업 로그, 도구 호출, 중간 분석과 결과를 대량으로 생성한다.

그러나 실제 사용자가 이를 하나하나 읽는 경우는 드물다.

Agent의 모든 내부 과정을 보여주는 것은 투명성과 동일하지 않다.

과도한 로그는 오히려 다음 문제를 만든다.

- 중요한 판단 지점을 찾기 어렵다.
- 사용자는 결과를 검증하지 않고 지나간다.
- 어떤 중간 결과가 최종 결과에 영향을 줬는지 알기 어렵다.
- 책임과 승인 지점이 불분명해진다.
- 다른 사람에게 업무 과정을 설명하기 어렵다.

Relay는 모든 과정을 노출하는 대신 **업무적으로 의미 있는 체크포인트를 만든다.**

# 3. Relay의 근본적 통찰

## 3.1 Agent의 내부 루프와 사람의 업무 루프는 다르다

Agent 내부에서는 다음과 같은 루프가 일어난다.

```text
판단
→ 도구 사용
→ 결과 관찰
→ 계획 수정
→ 다시 실행
```

이 내부 루프는 Agent가 각 Task를 수행하는 방법이다.

일반 사용자가 이 루프를 직접 설계하거나 지속적으로 감독할 필요는 없다.

사람에게 필요한 것은 더 높은 수준의 업무 루프다.

```text
업무 목적 정의
→ Task 분해
→ Task 실행
→ 결과물 생성
→ 검증
→ 승인 또는 보완
→ 다음 Task로 전달
→ 최종 결과 평가
→ 피드백을 설계에 반영
```

Relay는 Agent의 내부 추론 루프를 설계하는 도구가 아니다.

Relay는 **사람과 Agent가 함께 수행하는 업무 루프를 설계하는 도구**다.

## 3.2 Task 내부에서는 Agent를 신뢰하고, Task 경계에서는 결과를 확인한다

Agent의 수행 능력이 향상될수록 사람이 모든 세부 행동을 지시할 필요는 줄어든다.

그러나 이것이 아무런 통제 없이 최종 결과만 받아야 한다는 뜻은 아니다.

Relay가 지향하는 신뢰 모델은 다음과 같다.

> Agent가 제한된 Task 안에서는 자율적으로 일하도록 허용하되, 결과물이 다음 단계로 넘어가기 전에 검증 가능한 상태로 남게 한다.

따라서 Task의 경계는 단순한 실행 구분이 아니다.

Task의 경계는 다음을 확인하는 **업무 체크포인트**다.

- 요청한 결과물이 생성됐는가
- 결과물의 형식과 필수 조건이 충족됐는가
- 근거 자료가 연결돼 있는가
- 다른 Agent의 검증이 필요한가
- 사람의 판단과 승인이 필요한가
- 다음 단계의 입력으로 사용할 수 있는가
- 문제가 있다면 어느 단계부터 다시 수행해야 하는가

## 3.3 Session은 일시적이지만 업무 기록은 지속돼야 한다

Relay에서 Session은 필요할 수 있다.

Agent가 질문하거나, 사용자가 추가 지시를 내리거나, 검토 의견을 주고받는 과정에는 대화가 사용될 수 있다.

그러나 Session은 업무 기록의 중심이 아니다.

> **Session은 상호작용 수단이고, Task·Task Run·Artifact·Decision이 업무 기록의 원장이다.**

Task 내부의 상세 맥락은 실패 분석이나 감사가 필요할 때 확인할 수 있는 진단 자료다.

사용자가 일상적으로 확인해야 할 기본 정보는 다음이다.

1. 업무 목적
2. 입력 자료
3. 실행 상태
4. 출력 결과물
5. 검증 결과
6. 승인과 피드백
7. 다음 단계와의 관계

# 4. 오래된 조직 협업 프로토콜의 AI 시대적 재구성

Relay가 새롭게 발명하려는 것은 인간 협업의 원리 자체가 아니다.

회사와 조직은 오랫동안 다음 프로토콜로 일해 왔다.

```text
Mission
→ Delegation
→ Authority
→ Execution
→ Result
→ Evaluation
→ Feedback
```

한국어로 표현하면 다음과 같다.

```text
미션 정의
→ 업무 위임
→ 권한 부여
→ 수행
→ 결과 제출
→ 결과 평가
→ 피드백과 개선
```

AI Agent와의 협업에서도 이 구조는 유효하다.

오히려 Agent의 자율성이 커질수록 이 구조가 더 중요해진다.

## 4.1 Mission — 무엇을 달성하려는가

Mission은 단순한 프롬프트가 아니다.

Mission은 사람이 달성하려는 실제 업무 목적이다.

예:

- 이번 분기 경쟁사 전략 변화를 분석해 경영진에게 보고한다.
- 고객 불만의 주요 원인을 찾아 개선 우선순위를 정한다.
- 월간 실적을 분석하고 이상징후와 대응안을 제시한다.
- 신규 시장 진입 가능성을 조사하고 의사결정 자료를 만든다.

Relay에서 Mission의 기본 단위는 `Project`다.

## 4.2 Delegation — 누구에게 무엇을 맡기는가

하나의 Mission은 여러 세부 업무로 나뉜다.

```text
자료 수집
정보 정리
비교 분석
위험 평가
대안 작성
보고서 생성
```

각 세부 업무는 `Task`로 정의된다.

Task는 재사용 가능한 업무 정의이며, Agent에게 위임할 수 있는 명확한 책임 단위다.

## 4.3 Authority — 어떤 권한과 자원을 허용하는가

업무를 위임할 때는 수행 범위와 권한이 함께 정의돼야 한다.

- 접근 가능한 파일
- 사용할 수 있는 도구
- 허용된 외부 서비스
- 수정할 수 있는 경로
- 사용 가능한 Agent와 모델
- 비용·시간 제한
- 자동 진행 가능한 범위
- 사람 승인이 필요한 행동

Agent에게 업무를 맡기는 것은 무제한 권한을 주는 것이 아니다.

> **Task는 책임의 단위이면서 동시에 권한의 경계다.**

## 4.4 Execution — Agent가 자율적으로 수행한다

권한과 결과 기준이 정해지면 Agent는 Task 안에서 자율적으로 일한다.

사람은 Agent의 모든 도구 호출과 판단을 실시간으로 통제하지 않는다.

Agent는 필요에 따라:

- 자료를 탐색하고
- 파일을 읽고
- 분석하고
- 도구를 사용하고
- 오류를 수정하고
- 결과물을 생성한다.

Relay는 그 실행을 `Task Run`으로 기록한다.

## 4.5 Result — 업무 결과를 제출한다

업무의 결과는 단순한 채팅 답변이 아니다.

결과는 명확한 `Artifact`로 남는다.

예:

- 보고서
- 표
- 데이터셋
- 분석 JSON
- 프레젠테이션
- 검증 보고서
- 이미지
- 수정된 문서
- 의사결정안

Artifact는 생성한 Task Run, 사용한 입력, 검증 상태와 연결돼야 한다.

## 4.6 Evaluation — 결과를 평가한다

결과 평가는 여러 방식으로 이루어진다.

- 형식 검증
- 필수 항목 검증
- 규칙 기반 검증
- 다른 Agent의 독립 검증
- 사람의 검토
- 승인 또는 거절
- 후속 결과를 통한 실제 성과 평가

실행이 기술적으로 성공한 것과 업무 결과가 승인된 것은 구분돼야 한다.

## 4.7 Feedback — 다음 실행과 설계를 개선한다

피드백은 Session에만 남아서는 안 된다.

반복되는 피드백은 다음에 반영돼야 한다.

- Task 지침
- 입력 형식
- 출력 계약
- 검증 기준
- Agent 정책
- 승인 지점
- Project Design
- 실패 처리와 보완 루프

> **좋은 피드백은 다음 대화를 길게 만드는 것이 아니라 다음 업무 설계를 더 좋게 만든다.**

# 5. Relay의 중심 객체

## 5.1 Project

`Project`는 사람이 달성하려는 실제 업무다.

Project는 단순히 Task들을 담는 폴더가 아니다.

Project에는 다음이 포함된다.

- 목적
- 기대하는 최종 결과
- 완료 기준
- 책임자
- 관련 자료
- 현재 승인된 Project Design
- 과거 Project Run
- 최종 Artifact

예:

> 최근 8주간 시장 신호의 변화를 분석하고, 변화 원인과 향후 대응안을 포함한 경영진 보고서를 만든다.

## 5.2 Project Design

`Project Design`은 Project를 수행 가능한 구조로 만든 업무 설계다.

Project Design은 다음을 정의한다.

- 어떤 Task들이 필요한가
- 어떤 순서로 수행하는가
- 어떤 Task를 병렬로 수행할 수 있는가
- 각 Task는 무엇을 입력으로 받는가
- 무엇을 결과물로 만들어야 하는가
- 결과를 어떻게 검증하는가
- 어디에서 사람의 승인이 필요한가
- 문제가 있을 때 어떤 Task가 보완하는가
- 반복 실패 시 누구에게 판단을 요청하는가
- 최종 결과물이 어떻게 만들어지는가

Project Design은 단순한 Task 목록이 아니다.

> **Project Design은 업무의 책임·입력·출력·검증·승인·예외 처리를 명시한 실행 가능한 업무 프로토콜이다.**

## 5.3 Project Design Version

업무 설계는 변경될 수 있다.

그러나 이미 승인되고 실행된 설계를 덮어쓰면 안 된다.

Project Design이 변경되면 새로운 Version을 만든다.

이를 통해 다음을 구분할 수 있다.

- 업무 환경이 달라졌는가
- Task의 내용이 달라졌는가
- 검증 기준이 강화됐는가
- 승인 단계가 추가됐는가
- 결과 변화가 설계 변경 때문인가

승인된 Project Run은 실행 당시의 Project Design Version을 계속 참조해야 한다.

## 5.4 Project Run

`Project Run`은 특정 Project Design Version이 한 번 실행된 기록이다.

Project Run은 다음을 포함한다.

- 실행 목적과 시작 이유
- 사용한 Project Design Version
- 입력 Parameter와 Artifact
- 각 Node의 실행 상태
- 포함된 Task Run
- 승인 대기 상태
- 검증 결과
- 설계 변경 제안
- 최종 결과
- 시작·완료 시간
- 책임자와 승인자

## 5.5 Task

`Task`는 재사용 가능한 세부 업무 정의다.

예:

- 최근 뉴스 수집
- 자료 구조화
- 전주 결과와 비교
- 핵심 변화 추출
- 데이터 정확성 검증
- 경영진 보고서 작성

Task는 프롬프트와 동일하지 않다.

Task에는 다음이 포함될 수 있다.

- 목적
- 입력 Contract
- 수행 지침
- 출력 Contract
- 기본 Agent 정책
- 검증 기준
- 권한 범위
- 시간과 비용 제한
- 실패 처리 정책

## 5.6 Task Run

`Task Run`은 Task가 한 번 수행된 불변의 실행 기록이다.

Task Run에는 실행 당시 조건이 snapshot으로 남아야 한다.

- 사용한 Task Version
- 입력값
- 입력 Artifact
- 실행 Agent와 모델
- 권한과 도구
- 시작·종료 시각
- Attempt
- 출력 Artifact
- 검증 결과
- 승인 상태
- 오류와 이벤트

같은 Task는 여러 Task Run을 가질 수 있다.

```text
Task: 주간 시장 신호 분석

├─ Task Run: 7월 1주
├─ Task Run: 7월 2주
├─ Task Run: 7월 3주
└─ Task Run: 7월 4주
```

이 구조가 있어야 실행 결과의 시계열 비교와 변화 분석이 가능하다.

## 5.7 Attempt

`Attempt`는 하나의 Task Run 안에서 특정 Agent가 수행한 개별 시도다.

```text
Task Run
├─ Attempt 1: Claude → 인증 실패
├─ Attempt 2: Codex → 시간 초과
└─ Attempt 3: 다른 Agent → 완료
```

Agent는 업무 기록의 중심이 아니다.

Agent는 Task Run을 수행하기 위해 선택되는 교체 가능한 실행 자원이다.

## 5.8 Artifact

`Artifact`는 Task Run이 사용하거나 생성한 결과물이다.

Artifact는 단순한 파일 경로가 아니다.

Artifact에는 다음 관계가 있어야 한다.

- 누가 만들었는가
- 어떤 Task Run이 만들었는가
- 어떤 입력을 사용했는가
- 어떤 Task Run에서 다시 사용됐는가
- 어떤 검증을 통과했는가
- 어떤 버전이 승인됐는가
- 최종 결과에 어떻게 기여했는가

## 5.9 Artifact Lineage

Artifact는 다음 Task의 명시적인 입력이 된다.

```text
자료 목록
→ 구조화 데이터의 입력

구조화 데이터
→ 변화 분석의 입력

변화 분석
→ 영향 평가의 입력

영향 평가
→ 최종 보고서의 입력
```

Relay는 이 관계를 Session의 암묵적인 맥락으로 처리하지 않는다.

DB에 명시적인 관계로 기록한다.

```text
Artifact A
→ Task Run B의 Input
→ Artifact B 생성
```

이것이 결과물의 계보인 `Artifact Lineage`다.

## 5.10 Routine

`Routine`은 Task 또는 Project를 반복적으로 실행하는 등록이다.

Task와 Routine은 분리된다.

```text
Task:
주간 경쟁사 동향 분석

Routine:
매주 월요일 오전 8시에 실행
```

반복 실행의 결과는 매번 독립된 Task Run 또는 Project Run으로 남는다.

# 6. Project Design의 구성요소

## 6.1 Task Node

실제 업무를 수행하는 단계다.

각 Task Node는 다음을 명시한다.

- 사용할 Task와 Version
- 입력 Binding
- 출력 Contract
- Agent 정책
- 완료 조건
- 실패 처리
- 다음 단계

## 6.2 Verification Node

앞 단계 결과물을 다른 Agent 또는 검증 규칙으로 확인하는 단계다.

검증은 원래 Task의 내부 자기검토와 분리하는 것이 원칙이다.

```text
분석 작성
Agent A

→ 분석 검증
Agent B
```

검증 결과는 구조화된 판정을 포함해야 한다.

- `pass`
- `revise`
- `fail`
- 점수
- 발견된 문제
- 문제의 심각도
- 근거 Artifact
- 권장 보완사항

## 6.3 Approval Gate

사람의 판단이 필요한 체크포인트다.

Approval Gate에서는 다음 결정을 할 수 있다.

- 승인하고 다음 단계 진행
- 수정 요청
- 거절
- 사람 수정본으로 교체
- 의견을 첨부해 조건부 승인
- 지정된 이전 단계부터 재실행

승인은 특정 Artifact Version을 대상으로 한다.

승인된 Artifact가 변경되면 기존 승인은 더 이상 유효하지 않다.

## 6.4 Decision Node

조건에 따라 실행 경로를 결정한다.

예:

```text
검증 통과
→ 사람 승인

수정 필요
→ 보완 Task

심각한 실패
→ 사람에게 Escalation
```

Decision은 자연어 판단만으로 숨겨져서는 안 된다.

판정 기준과 선택된 경로가 기록돼야 한다.

## 6.5 Remediation Node

검증 또는 사람의 피드백에서 발견된 문제를 수정하는 단계다.

```text
초안 v1
→ 검증
→ 문제 발견
→ 보완
→ 초안 v2
→ 재검증
```

원본 Artifact를 덮어쓰지 않는다.

각 Version과 변경 이유를 남긴다.

## 6.6 Feedback Loop

Project Design은 단방향 DAG에만 머물지 않는다.

다음과 같은 통제된 반복을 지원해야 한다.

```text
결과 생성
→ 검증
→ 기준 미달
→ 보완
→ 재검증
```

루프에는 반드시 제한이 있어야 한다.

- 최대 반복 횟수
- 최대 비용
- 최대 시간
- 중단 조건
- 사람에게 Escalation할 조건

Relay의 루프는 Agent가 무제한으로 자기 작업을 반복하는 구조가 아니다.

> **Relay의 루프는 검증 기준과 책임 경계를 가진 업무 피드백 루프다.**

## 6.7 Design Amendment

실행 중 예상하지 못한 단계가 필요할 수 있다.

Agent는 승인된 Project Design을 임의로 변경하지 않는다.

대신 `Design Amendment`를 제안한다.

예:

```text
제안:
자료 신뢰성 검증 Task 추가

이유:
세 개 출처의 수치가 충돌함

영향:
Task 한 개 추가
예상 실행시간 15분 증가
최종 분석 전 사람 승인 필요
```

사람은 다음 중 하나를 선택한다.

- 이번 Project Run에만 적용
- 새로운 Project Design Version으로 반영
- 거절
- 수정 후 승인

# 7. 사람과 Agent의 역할

## 7.1 사람의 역할

Relay에서 사람은 Agent의 모든 행동을 지시하는 Operator가 아니다.

사람은 다음 역할을 가진다.

- Mission을 정의한다.
- Project의 완료 기준을 정한다.
- Project Design을 만들거나 검토한다.
- Task의 책임과 권한 범위를 정한다.
- 중요한 체크포인트를 선택한다.
- 검증과 승인 기준을 정한다.
- 예외와 갈등 상황을 판단한다.
- 최종 결과에 책임을 진다.
- 반복되는 피드백을 설계에 반영한다.

사람은 **업무 설계자, 감독자, 평가자, 책임자**다.

## 7.2 Agent의 역할

Agent는 다음을 수행할 수 있다.

- Mission을 분석한다.
- Project Design 초안을 제안한다.
- 기존 Task를 검색하고 재사용한다.
- 필요한 Task를 새로 정의한다.
- Task 간 입력과 출력을 연결한다.
- Project Design의 오류를 검증한다.
- Task를 실행한다.
- 결과물을 생성한다.
- 다른 Agent의 결과물을 검증한다.
- 오류를 보완한다.
- 새로운 검증 단계나 설계 변경을 제안한다.
- 사람이 판단해야 할 문제를 Escalation한다.

Agent는 업무를 대신 수행할 수 있고, 업무 설계도 제안할 수 있다.

그러나 중요한 업무 설계와 권한 변경은 기본적으로 사람의 승인을 거친다.

---

# 8. Headless CLI와 GUI의 역할

## 8.1 Headless CLI는 Agent의 업무 인터페이스다

Agent는 Relay를 headless CLI 또는 안정된 machine API로 사용할 수 있어야 한다.

Agent는 다음 작업을 수행할 수 있어야 한다.

- Task 검색
- 과거 Task Run 검색
- Artifact 검색과 조회
- Project 생성
- Project Design 초안 작성
- Task Node 추가
- 입력·출력 연결
- Verification Node 추가
- Approval Gate 추가
- Design 검증
- Design Amendment 제안
- Project Run 실행과 상태 확인
- 결과 비교
- 특정 Node부터 부분 재실행

CLI는 사람에게 복잡한 명령어를 학습시키기 위한 기능이 아니다.

> **Headless CLI는 Agent가 Relay의 업무 기억과 실행 기능을 안전하게 사용하는 프로토콜이다.**

## 8.2 GUI는 업무 구조를 사람이 이해하게 하는 인터페이스다

GUI에서는 Project Design을 직관적으로 볼 수 있어야 한다.

사용자는 다음을 한 화면에서 이해할 수 있어야 한다.

- Project의 목적
- 전체 Task 구조
- 현재 실행 위치
- 완료된 단계
- 실행 중인 단계
- 대기 중인 단계
- 사람 승인을 기다리는 단계
- 실패하거나 보완 중인 단계
- 각 단계의 입력과 출력 Artifact
- 검증 결과
- 최종 결과가 만들어진 경로

예:

```text
[자료 수집] ✓
      │ sources.zip
      ▼
[정보 구조화] ✓
      │ normalized.json
      ▼
[독립 검증] ✓ Pass
      │
      ▼
◇ 사람 승인 ◇ Approved
      │
      ▼
[영향 분석] ✓
      │ impact.md
      ▼
[최종 보고서] ✓
      └─ executive_report.pptx
```

GUI는 Agent의 숨겨진 추론을 시각화하는 도구가 아니다.

GUI는 **업무 설계, 실행 상태, 결과물 흐름과 책임 지점을 시각화하는 도구**다.

# 9. 신뢰에 대한 Relay의 관점

## 9.1 신뢰는 모든 생각을 보는 데서 나오지 않는다

사람은 다른 동료의 모든 생각과 행동을 실시간으로 관찰하지 않는다.

대신 다음으로 신뢰를 형성한다.

- 명확한 업무 위임
- 적절한 권한
- 합의된 결과 기준
- 중간 보고
- 결과물 검토
- 독립적인 검증
- 피드백에 대한 개선
- 반복 수행에서의 일관성

AI Agent와의 신뢰도 동일한 방식으로 형성될 수 있다.

## 9.2 설명 가능성은 업무 구조에서 나온다

다른 사람이나 상사에게 다음과 같이 말하는 것은 설득력이 약하다.

> AI에게 자료를 넣고 분석해 달라고 했습니다.

Relay에서는 다음과 같이 설명할 수 있어야 한다.

> 먼저 관련 자료를 수집했습니다.  
> 수집 결과를 동일한 기준으로 구조화했습니다.  
> 지난 기간 결과와 비교해 주요 변화만 추출했습니다.  
> 별도 Agent가 근거와 누락 항목을 검증했습니다.  
> 담당자가 검증 결과와 중간 Artifact를 승인했습니다.  
> 승인된 결과만 사용해 최종 보고서를 만들었습니다.

각 설명에는 실제 Task Run과 Artifact가 연결돼 있다.

이것이 조직에서 사용할 수 있는 설명 가능성이다.

## 9.3 검증 가능한 중간 결과가 최종 결과의 신뢰를 만든다

기존의 Agent 제품은 여러 Sub-agent가 내부에서 작업한 뒤 최종 결과만 전달하는 경우가 많다.

사용자는 다음을 확인하기 어렵다.

- 어떤 세부 업무가 수행됐는가
- 어떤 단계에서 오류가 발생했는가
- 어떤 중간 결과가 최종 결론의 근거인가
- 특정 단계만 다시 수행할 수 있는가
- 검증되지 않은 정보가 최종 결과에 섞였는가

Relay에서는 각 Task Run의 결과물이 독립적으로 관리된다.

따라서 최종 결과의 신뢰도는 단순히 Agent를 믿는 데서 나오지 않는다.

> **최종 결과가 검증된 중간 결과물들의 명시적인 연결로 만들어졌다는 사실에서 나온다.**

# 10. 검색 가능한 업무 기억

Relay는 과거 업무를 단순 보관하지 않는다.

Agent와 사람이 다시 활용할 수 있도록 검색 가능한 업무 기억으로 만든다.

예:

> 이번 주 `abc` Task Run들의 결과물을 찾아 신호 강도 추이의 변화를 분석하라.

Agent는 Relay에서 다음을 찾을 수 있어야 한다.

- `abc` Task
- 이번 주에 수행된 Task Run
- 성공한 실행
- 각 실행의 출력 Artifact
- 실행 당시 Task Version
- 검증 및 승인 상태
- 이전 결과를 사용한 후속 Task
- 결과에 포함된 주요 지표

이렇게 과거 업무 기록 자체가 새로운 Task의 입력이 된다.

```text
과거 Task Run
→ Artifact 검색
→ 비교 분석 Task
→ 새로운 Artifact
```

Relay는 대화를 기억하는 제품이 아니라 **업무가 무엇을 만들었는지를 기억하는 제품**이다.

---

# 11. Work Agent로서 Relay의 차별점

Relay의 차별점은 단순히 Task 기능이 있다는 것이 아니다.

차별점은 다음 요소의 결합이다.

## 11.1 Session보다 지속되는 업무 구조

Session이 종료돼도 다음은 남는다.

- Task
- Project Design
- Task Run
- Project Run
- Artifact
- 검증
- 승인
- 피드백
- Lineage

## 11.2 Agent보다 지속되는 업무 기록

Claude, Codex 또는 다른 Agent가 교체돼도 업무 정의와 실행 기록은 유지된다.

Agent는 수행자다.

Relay가 보존하는 핵심 자산은 **업무와 결과의 조직적 기억**이다.

## 11.3 결과물 중심의 명시적 연결

다음 Task는 이전 Session의 맥락을 암묵적으로 이어받지 않는다.

승인되거나 선택된 Artifact를 명시적인 입력으로 받는다.

## 11.4 검증과 승인까지 포함한 실행

Relay에서 자동화는 실행으로 끝나지 않는다.

검증, 보완, 승인, Escalation과 평가가 업무 흐름에 포함된다.

## 11.5 부분 재실행과 수정 가능성

최종 결과에 문제가 생겨도 전체 Project를 다시 시작할 필요가 없다.

문제가 발생한 Task와 그 결과에 의존하는 후속 단계만 다시 수행할 수 있다.

## 11.6 Agent가 업무 시스템 자체를 사용할 수 있음

Agent는 Relay의 CLI와 API를 사용해 다음을 수행한다.

- 기존 업무 찾기
- 과거 결과 분석
- Project Design 작성
- 업무 실행
- 결과 검증
- 설계 변경 제안

Relay는 Agent를 실행하는 앱이면서, Agent가 사용하는 **업무 운영 도구**다.

# 12. 제품 원칙

## 원칙 1. Project는 실제 업무 목적이다

제품의 최상위 개념은 Session이나 Agent가 아니라 Project다.

## 원칙 2. Task는 책임과 권한의 단위다

Task는 수행할 일뿐 아니라 Agent가 사용할 수 있는 자원과 기대 결과를 정의한다.

## 원칙 3. Task Run은 불변의 실행 기록이다

완료된 Task Run을 수정하지 않는다.

수정과 재실행은 새로운 Task Run으로 남긴다.

## 원칙 4. Artifact가 업무 단계 사이를 이동한다

암묵적 대화 맥락이 아니라 명시적인 Artifact 관계로 입력과 출력을 연결한다.

## 원칙 5. 모든 중요한 결과에는 출처가 있어야 한다

최종 Artifact에서 이를 만든 Task Run, 입력 Artifact, 검증과 승인 기록으로 이동할 수 있어야 한다.

## 원칙 6. 자율성은 Task 내부에 부여한다

Agent는 Task 안에서 수행 방법을 선택할 수 있다.

그러나 입력, 출력, 권한과 완료 기준은 명확해야 한다.

## 원칙 7. 사람은 모든 단계를 승인하지 않는다

사람 승인은 책임·위험·판단이 필요한 지점에만 둔다.

낮은 위험의 단계는 자동 진행하고, 검증 가능한 단계는 다른 Agent나 규칙으로 확인한다.

## 원칙 8. Agent의 자기검토와 독립 검증을 구분한다

중요한 결과의 검증은 가능하면 별도의 Task Run과 별도의 Agent로 수행한다.

## 원칙 9. 반복에는 제한과 Escalation이 있어야 한다

모든 보완 루프에는 최대 횟수, 시간, 비용과 사람 판단 조건이 있어야 한다.

## 원칙 10. 피드백은 설계에 축적한다

반복되는 피드백은 Session에 묻어두지 않고 Task 또는 Project Design의 새 Version으로 반영한다.

## 원칙 11. GUI와 CLI는 같은 업무 원장을 사용한다

사람이 GUI에서 보는 Project와 Agent가 CLI에서 다루는 Project는 동일해야 한다.

별도의 자동화용 이력과 사용자용 이력을 만들지 않는다.

## 원칙 12. 기술 로그는 필요할 때 접근한다

로그, stdout, stderr와 세부 이벤트는 보존한다.

그러나 기본 사용자 경험은 목적, 결과, 검증과 승인 중심이어야 한다.

---

# 13. Relay가 지향하지 않는 것

## 13.1 모든 생각을 보여주는 Agent 관찰기

긴 추론 로그를 보여주는 것이 제품의 핵심 가치가 아니다.

## 13.2 Coding Agent의 외형만 바꾼 업무 앱

Repository, Branch, Terminal과 Session을 일반 업무에 그대로 적용하지 않는다.

일반 업무에 맞는 Project, Task, Artifact, Approval과 Feedback 모델을 중심으로 설계한다.

## 13.3 무제한 자율 Agent 시스템

Agent가 목적, 권한, 검증 없이 계속 실행되는 구조를 지향하지 않는다.

## 13.4 단순한 Workflow Builder

Relay는 Node를 연결하는 시각적 자동화 도구에 그치지 않는다.

각 Node의 실행 기록, 결과물, 검증, 승인과 피드백을 업무 기억으로 남긴다.

## 13.5 단순한 파일 관리자

파일은 Artifact의 저장 형태 중 하나다.

Relay의 핵심은 파일을 생성한 업무와 이후의 사용 관계를 관리하는 것이다.

## 13.6 단순한 Chat History

과거 대화 검색보다 과거 Task Run과 Artifact 검색을 우선한다.

---

# 14. 핵심 사용자

Relay의 초기 핵심 사용자는 다음과 같다.

> AI를 실제 업무에 반복적으로 사용하며, 조사·분석·보고서·평가 결과를 계속 축적하고 비교해야 하는 사람.

대표적인 업무는 다음과 같다.

- 전략과 경쟁사 분석
- 투자 및 산업 리서치
- 재무와 실적 분석
- 영업 성과와 파이프라인 분석
- 마케팅 성과 평가
- 고객 VOC 분석
- 구매와 공급망 위험 분석
- 인사와 채용시장 분석
- 운영·품질 점검
- 정기 보고서 작성
- 문서 검토와 승인

코더는 Relay의 중요한 사용자일 수 있다.

그러나 Relay의 제품 정체성은 Coding Agent 관리자가 아니다.

Relay는 **반복되는 지식업무를 설계하고 검증해야 하는 조직 구성원**을 위한 Work Agent다.

---

# 15. 제품 성공의 기준

Relay의 성공은 Agent가 얼마나 많은 행동을 자동화했는지만으로 평가하지 않는다.

다음 질문으로 평가한다.

- 사용자가 실제 Mission을 Project로 표현할 수 있는가
- Agent가 Project Design 초안을 만들 수 있는가
- 사람이 그 설계를 쉽게 이해하고 승인할 수 있는가
- 각 Task의 입력과 출력이 명확한가
- 중요한 결과가 검증됐는가
- 사람의 승인이 필요한 지점이 적절한가
- 최종 결과의 근거를 추적할 수 있는가
- 잘못된 단계만 다시 실행할 수 있는가
- 과거 실행 결과를 검색하고 비교할 수 있는가
- 피드백이 다음 Project Run에서 자동으로 활용되는가
- 다른 사람에게 업무 과정과 결과를 설명할 수 있는가

---

# 16. 기능 결정에 사용하는 최상위 질문

새로운 기능을 제안할 때는 다음을 확인한다.

### 업무 설계를 더 명확하게 만드는가?

아니면 단지 Agent의 세부 행동을 더 많이 보여주는가?

### Task의 책임과 결과 경계를 강화하는가?

아니면 Session에 더 많은 맥락을 쌓는가?

### Artifact의 출처와 사용 관계를 보존하는가?

아니면 파일만 복사하는가?

### 사람이 적절한 지점에서 판단할 수 있게 하는가?

아니면 사람을 모든 실행에 개입시키는가?

### 실패한 일부 단계만 수정할 수 있게 하는가?

아니면 전체 업무를 다시 시작하게 하는가?

### Agent와 사람이 같은 업무 구조를 보고 있는가?

아니면 자동화 내부에 숨겨진 별도 흐름을 만드는가?

### 반복되는 피드백을 설계에 축적하는가?

아니면 다음 Session에서 다시 설명하게 만드는가?

이 질문에 긍정적으로 답하지 못하는 기능은 Relay의 핵심 우선순위가 아니다.

# 17. 공식 용어

| 용어 | 정의 |
|---|---|
| **Mission** | 사람이 달성하려는 상위 목적 |
| **Project** | Mission을 수행하고 최종 결과를 만드는 실제 업무 |
| **Project Design** | Task, Artifact 흐름, 검증, 승인과 예외 처리를 포함한 실행 가능한 업무 설계 |
| **Project Design Version** | 특정 시점에 승인된 불변의 업무 설계 |
| **Project Run** | Project Design Version이 한 번 실행된 기록 |
| **Task** | 재사용 가능한 세부 업무 정의 |
| **Task Version** | 특정 시점의 Task 지침과 입출력 계약 |
| **Task Run** | Task가 한 번 실행된 기록 |
| **Attempt** | Task Run 안에서 특정 Agent가 수행한 개별 시도 |
| **Artifact** | Task Run이 입력으로 사용하거나 출력한 결과물 |
| **Artifact Lineage** | Artifact가 생성되고 다음 업무에 사용된 관계 |
| **Verification** | 결과물이 기준을 충족하는지 독립적으로 확인하는 업무 |
| **Approval Gate** | 사람의 판단과 승인이 필요한 체크포인트 |
| **Remediation** | 검증이나 피드백에서 발견된 문제를 보완하는 업무 |
| **Design Amendment** | 실행 중 제안되는 Project Design 변경 |
| **Routine** | Task 또는 Project의 반복 실행 등록 |
| **Session** | 업무 수행 중 일시적으로 이루어지는 대화와 상호작용 |
| **Agent** | Task Run을 수행하거나 검증하는 교체 가능한 실행 주체 |

`Job`은 신규 사용자 정신모델의 중심 용어로 사용하지 않는다.

# 18. Relay 선언문

우리는 AI가 더 많은 생각을 출력하도록 만드는 것이 아니라, 더 나은 업무를 수행하도록 만들고자 한다.

우리는 사람이 Agent의 모든 행동을 감시해야 한다고 생각하지 않는다.

우리는 Agent가 모든 업무를 한 번에 수행하고 최종 결과만 전달하는 방식도 충분하지 않다고 생각한다.

업무는 목적에서 시작한다.

목적은 책임 있는 Task로 나뉜다.

Task는 명확한 입력을 받고 결과물을 만든다.

중요한 결과물은 검증된다.

책임이 필요한 지점에서는 사람이 승인한다.

문제가 발견되면 필요한 단계만 보완한다.

승인된 결과물은 다음 Task의 입력이 된다.

최종 결과는 검증된 중간 결과물들의 연결로 만들어진다.

모든 실행, 결과, 평가와 피드백은 다음 업무를 위한 기억으로 남는다.

사람은 AI에게 계속 말을 거는 운영자가 아니라, 업무의 목적과 구조를 설계하고 중요한 판단에 책임지는 사람이 된다.

Agent는 사람을 대체하는 하나의 거대한 Black Box가 아니라, 명확한 책임과 권한을 가진 업무 수행자가 된다.

Relay는 이 둘 사이의 오래된 협업 원칙을 AI 시대에 맞게 구현한다.

```text
Mission
→ Delegation
→ Authority
→ Execution
→ Result
→ Evaluation
→ Feedback
→ Better Design
```

> **Relay는 Agent의 모든 생각을 감독하지 않는다.  
> Relay는 업무를 설계하고, 결과물을 확인하며, 신뢰 가능한 협업 루프를 만든다.**
